Privacy and data handling

Privacy Policy

This policy explains how Luminary AI Engine handles browser conversations, API credentials, third-party model requests, optional telemetry and opt-in research data.

Last updated: 12 November 2026

Important distinction: The standalone browser application and the optional self-hosted Express API have different data paths. No-Log Mode controls browser telemetry and requests eligible OpenRouter ZDR routing; it does not mean that every third-party service or optional API deployment stores no operational data.

1. Who publishes the Engine

Luminary AI Engine is a project published and maintained by Luminary Technicals. The public website is an interface and orchestration layer for multi-model prompt engineering. Model inference is provided by third-party services rather than by a Luminary-owned foundation model.

2. Standalone browser application

The standalone app stores conversations, preferences and settings in browser storage on the device. It does not provide a Luminary account or automatic cloud synchronisation. Clearing browser data or site storage may permanently delete local conversations and settings.

The user's OpenRouter API key is stored in browser storage in an encrypted representation when Web Crypto is available. Browser-side encryption does not protect against malicious same-origin JavaScript, a compromised device, or browser extensions that can access the page or its storage.

3. Model providers and prompt processing

When you run a model workflow, the relevant prompt, conversation context and request parameters are sent to OpenRouter and, as routed, the selected upstream model provider. Your API key is used to authenticate the request. The handling, retention and processing of those requests by OpenRouter and upstream providers are governed by their own terms and privacy policies.

Do not submit passwords, secrets, confidential business information or personal data unless you have the right to do so and have considered the provider's data-handling terms.

4. No-Log Mode

No-Log Mode is enabled by default in the standalone browser application. For supported chat-completion requests, the app asks OpenRouter for provider.zdr: true and provider.data_collection: "deny". These settings request eligible Zero Data Retention routing and deny providers that non-transiently collect request data. A request may fail when no eligible provider endpoint is available.

ZDR does not prevent a model provider from processing the request to generate a result, and it does not eliminate operational metadata that OpenRouter, hosting providers or network infrastructure may process under their own terms.

5. Optional browser performance telemetry

When No-Log Mode is enabled, the standalone app does not buffer or send its optional browser performance telemetry. If a user turns No-Log Mode off, the app may send allowlisted operational events such as timestamps, a session identifier, model and mode identifiers, durations, response length, success/failure status and pipeline configuration to the deployment's /api/telemetry endpoint.

The telemetry schema is designed for operational metrics, not prompt text or response content. Whether a telemetry endpoint is available and whether publishing is configured depends on the deployment.

6. Optional API-server metadata

The repository also contains an optional Express API server that can be self-hosted separately. For API requests, that server may record content-free operational metadata such as endpoint, model identifiers, mode, scores, durations, response length and success/failure categories. The API metadata path is separate from the standalone browser app's No-Log Mode.

If the deployment operator configures HF_TOKEN and HF_DATASET_REPO, buffered operational metadata may be published to the configured Hugging Face repository. The public static website should not be assumed to expose the optional API unless it is separately deployed.

7. Opt-in research dataset

The optional API accepts contribute_to_dataset: true. This is opt-in and is not enabled by default. When explicitly enabled, the API dataset code can store submitted non-system messages and the final response together with model and pipeline metadata.

The current dataset implementation does not include automatic PII scrubbing. Do not submit passwords, API keys, personal identifiers, health details, financial information or other sensitive data when dataset contribution is enabled. If Hugging Face publishing is configured, contributed content may become public and may be copied or redistributed.

8. Retention and deletion

Local conversations and settings remain in the browser until the user clears them or the browser removes them. Optional API metadata and dataset buffers are held in server memory subject to configured limits and may be lost on restart if not published.

Dataset entries can be deleted through the optional API while they remain in its in-memory buffer. Deletion from that buffer cannot remove copies that have already been published, downloaded, cached, forked or redistributed. Operational metadata does not currently provide an individual end-user deletion endpoint.

9. Cookies and browser technologies

The current application source does not intentionally set analytics or advertising cookies. It does use local storage and service-worker Cache Storage for application functionality and offline resources. These technologies are described separately in the Cookie Policy.

10. Contact and updates

For privacy questions or correction requests, contact legal@luminarytechnicals.dpdns.org or open an issue in the project repository. This policy may be updated as the application or its deployments change.
